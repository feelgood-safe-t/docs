## ⓘ 이 문서의 성격

**backend·frontend 저장소는 기획 담당의 관리 범위 밖이다.** 이 문서는 그 저장소들에 대한 과제 목록이 아니라,
**기획서·기능명세서를 사실에 맞게 쓰기 위해 구현 현황을 읽어둔 참고 메모**다.

용도는 세 가지다.
1. 기획서·기능명세서가 **실제 구현과 어긋나지 않도록** 하는 것 — 심사 제출물이므로 사실 정확성이 중요하다
2. 기획 문서에서 정의해야 할 것(평가 항목 정의, 채점 연결)의 **경계를 확인**하는 것
3. 담당자에게 **전달·확인할 사항**을 정리해 미팅에 올리는 것

> 여기 적힌 차이·이슈에 대한 **조치 판단은 각 저장소 담당의 몫**이다.

## 1. 백엔드 v0.4가 확정한 것 — 기존 미해결 안건 해소

`backend/docs/spec-alignment.md`가 2026-09-03자로 제품 요구사항을 v0.4로 갱신했다. 우리 문서의 열린 항목 여럿이 여기서 닫힌다.

| 우리 안건 | 백엔드 v0.4의 확정 내용 | 상태 |
|---|---|---|
| **C3** 미완료 감점 규칙 | 미응답 terminal item은 `UNANSWERED` → **후단 규칙 평가기에서 item 점수 0**. **조기 종료 자체에는 별도 penalty 없음.** 선택적 confidence·quiz 미제출만으로 감점하지 않음 | ✅ **해소** |
| **C2(a)** 진행 상태 저장 | 엔진이 서버(SQLite)에 세션·행동 이벤트를 append-only로 저장. 재접속 이어하기 가능 | ✅ **해소** — 프론트의 로컬 스토리지는 *결과 표시* 용도로 병존 |
| **R2** 판단 근거 필수화 | `reasonTags` 1개 이상 **또는** `reasonText` 1~500자 — **any-of 필수.** 둘 다 비면 `422 DECISION_REASON_REQUIRED` | ✅ 확정 |
| **Q1** 채점 재현성 (부분) | 엔진은 점수를 만들지 않는다. 평가 결과 서비스가 `snapshotHash`·`rubricVersion`·`promptVersion`·`modelVersion`과 구조화 출력 hash를 보존. **완전 결정성이 아니라 버전 고정 + 해시 보존** 방식 | 🟡 **부분 답변** — 동일 입력 재현 보장 수준은 여전히 확인 필요 |
| 방향 판정 기준 | 모든 의견을 **시장 시간 180분 후 결과 bar**와 비교. **10bp `TIE` 기준** | ✅ 신규 확정 |
| 미래정보 차단 | cutoff 이후 bar는 방향 비교에만, cutoff 이후 news는 **판단 과정 평가 LLM 입력에서 제외** | ✅ |

## 3. 🔴 A2 · 배점 50점의 측정 입력이 없다

### 3.1 레버리지 상품이 PoC 시나리오에 없다 — **가장 중요한 발견**

> **PoC Runtime Scenario에는 레버리지·인버스 상품을 넣지 않는다.**
> 관련 개념은 설문이나 선택적 quiz로 확인할 수 있다. 향후 해당 상품을 사용하려면 상품 유형·배수를 명시하는
> 별도 Scenario schema 변경이 먼저 필요하다. — `backend/docs/backend-engine-spec.md`

**기획 문서에 미치는 영향이 크다.**

| 영역 | 현재 기획 문서 서술 | 실제 PoC |
|---|---|---|
| 서비스명 | 「AI **레버리지** 안전투자 훈련 플랫폼」 | 레버리지 상품 없음 |
| 기획서 4.1 | *"자산 3개 — 일반 / 레버리지 또는 안정 / **레버리지·인버스**"* | item당 단일 자산, 레버리지 제외 |
| 배점 | 「레버리지 통제」 20점 | 행동으로 관찰 불가 |
| UI 와이어프레임 | `가온소재 2X`, 레버리지 노출 경고 밴드 | 해당 자산 없음 |
| 문제 정의 | 2026-08-19 단일종목 레버리지 이수 의무화 | *(문제 정의 자체는 유효 — 서비스가 겨냥하는 시장은 그대로)* |

> **문제 정의(3번)는 그대로 유효하다.** 레버리지 상품의 위험이 크다는 사회적 문제와, 그 훈련 도구를 만든다는 방향은 바뀌지 않는다.
> 조정이 필요한 것은 **"PoC에서 무엇을 구현했는가"**를 기술하는 부분이다 — 기능명세서는 규정상 *"구현된 것만"* 쓴다.

**선택지**
1. **시나리오에 레버리지를 포함**하도록 논의 → schema 변경이 선행돼야 하므로 마감까지 현실성 낮음
2. **기획서를 "1단계는 고변동 구간 대응, 레버리지 상품은 다음 단계"로 기술** → 정직하고 구현과 일치. **권장**
3. 서비스명에서 '레버리지'를 빼고 상위 개념으로 → 명칭 변경 비용

### 3.2 위험 한도 준수 20 · 자산 집중도 10

`backend-engine-spec.md`는 엔진이 다음을 **생성·추론하지 않는다**고 규범적으로 못 박는다.

> 주문, 보유량, 비중, 현금, 노출, 손익, MDD, 유효 레버리지, **집중도**

| 항목 | 배점 | 문제 |
|---|---|---|
| 위험 한도 준수 | 20 | 온보딩 문항이 **정성 3단계**(낮음/보통/높음)라 "한도 초과분"을 계산할 수 없다 |
| 자산 집중도 | 10 | **item당 자산이 하나면 개념 자체가 성립하지 않는다** |

### 3.3 어디서 정하는가

`evaluationPlanRef`가 가리키는 **외부 승인 rubric**이 *"각 평가 항목의 공개 정보·행동·시장 checkpoint와 증거 부재 처리 규칙"*을 정의하도록 되어 있다. **이 rubric은 아직 작성되지 않았고 담당도 미정이다.**

> 재정의 제안은 `03-survey/02-investor-profiling-questionnaire.md` §4.4 참조.

### 3.4 참고 — 온보딩 설문은 채점 근거가 아니다

엔진 스펙은 *"엔진은 응답을 **성향 값이나 위험 한도로 변환하지 않아야 한다**"*고 명시하고, 설문 해석은 **Selection Orchestrator**(시나리오 선택) 책임이다.
설문 원본이 Snapshot에 함께 봉인되므로(`payload.survey`) **보고서 서술에는 참조 가능**하지만, **점수 산출의 근거는 평가 중 행동 기록**이다.

## 5. ⚠️ A3 · 문서가 아직 팀의 참조 대상이 아니다

`backend/README.md`와 `spec-alignment.md`에 따르면

- backend는 제품 명세를 **`docs/product-spec` Git submodule**로 버전 고정한다
- 현재 pin 대상은 **docs `main`의 커밋 `fc412a0`** → `spec/README.md`
- *"upstream 문서는 `feelgood-safe-t/docs`에서 먼저 수정·검증·commit·push한 뒤 backend gitlink를 갱신한다"*

**따라서 우리 기획·리서치·설문·UI 문서는 아직 backend의 참조 대상이 아니다.** `docs/initial-planning-docs` 브랜치에만 있고 `main`에 머지되지 않았기 때문이다.

> ✅ **기획 담당이 할 수 있는 조치 — PR #1 머지 요청**
> https://github.com/feelgood-safe-t/docs/pull/1
> 머지되어야 ① 온보딩 설문 명세와 채점 연결이 팀의 공식 참조 대상이 되고 ② 팀 전체가 `main` 하나만 보면 된다.
> 이 저장소는 기획 담당의 관리 범위이므로 **머지 요청은 직접 진행 가능한 유일한 조치**다.

## 1. 백엔드 v0.4가 확정한 것 — 기존 미해결 안건 해소

`backend/docs/spec-alignment.md`가 2026-09-03자로 제품 요구사항을 v0.4로 갱신했다. 우리 문서의 열린 항목 여럿이 여기서 닫힌다.

| 우리 안건 | 백엔드 v0.4의 확정 내용 | 상태 |
|---|---|---|
| **C3** 미완료 감점 규칙 | 미응답 terminal item은 `UNANSWERED` → **후단 규칙 평가기에서 item 점수 0**. **조기 종료 자체에는 별도 penalty 없음.** 선택적 confidence·quiz 미제출만으로 감점하지 않음 | ✅ **해소** |
| **C2(a)** 진행 상태 저장 | 엔진이 서버(SQLite)에 세션·행동 이벤트를 append-only로 저장. 재접속 이어하기 가능 | ✅ **해소** — 프론트의 로컬 스토리지는 *결과 표시* 용도로 병존 |
| **R2** 판단 근거 필수화 | `reasonTags` 1개 이상 **또는** `reasonText` 1~500자 — **any-of 필수.** 둘 다 비면 `422 DECISION_REASON_REQUIRED` | ✅ 확정 |
| **Q1** 채점 재현성 (부분) | 엔진은 점수를 만들지 않는다. 평가 결과 서비스가 `snapshotHash`·`rubricVersion`·`promptVersion`·`modelVersion`과 구조화 출력 hash를 보존. **완전 결정성이 아니라 버전 고정 + 해시 보존** 방식 | 🟡 **부분 답변** — 동일 입력 재현 보장 수준은 여전히 확인 필요 |
| 방향 판정 기준 | 모든 의견을 **시장 시간 180분 후 결과 bar**와 비교. **10bp `TIE` 기준** | ✅ 신규 확정 |
| 미래정보 차단 | cutoff 이후 bar는 방향 비교에만, cutoff 이후 news는 **판단 과정 평가 LLM 입력에서 제외** | ✅ |

### 책임 경계 (백엔드 문서 기준)

## 2. 🔴 A1 · 세션 구조 — 백엔드는 확정, 프론트는 이전 구조

| | **backend v0.4** (9/3 확정) | **frontend** (구현 완료) | **9/2 미팅 노트** |
|---|---|---|---|
| 구조 | item **정확히 3개**, **순차 진행** | 자산 3개 **자유 이동** | 양쪽 서술이 모두 등장 |
| 자산 | **item당 단일 자산** | 화면당 3자산 캐러셀 | "3개 종목" |
| 시간 | **item당 180초** | **전체 6분** | "문항당 3분" / "6분 동안" |
| 조기 종료 | item 조기 완료 + 전체 종료 | 전체 종료 | 조기 종료 버튼 추가됨 |

**해석** — 충돌이라기보다, **미팅 다음 날 백엔드가 "포지션 없는 3문항" 구조로 문서를 확정했고 프론트에는 아직 반영되지 않은 상태**로 보인다. 백엔드 커밋 메시지 자체가 `specify positionless three-question assessment`다.

**영향**

| 영역 | 순차·단일 자산으로 확정될 경우 |
|---|---|
| 프론트 | `AssetTabs` 캐러셀 → **item 단계 진행형**으로 재작업. 이전 item 복귀 불가 |
| 우리 UI 문서 | `[T]` 와이어프레임의 자산 3개 캐러셀·판단 요약 바·스와이프 안내 재작성 |
| 구현 시안 | `assets/mockup-evaluation-screen.png`의 캐러셀 영역 재설계 |
| 채점 | 「자산 집중도」(10점)가 **성립하지 않는다** (item당 자산 1개) → §3 |

> ⏰ **9/6(토) 연동 마감 전에 반드시 확정.** 자산 3개 캐러셀로 연동해두면 백엔드가 item을 하나씩 주는 순간 연동이 깨진다.

## 3. 🔴 A2 · 배점 30점의 측정 방식이 정의되지 않았다

`backend-engine-spec.md`는 엔진이 다음을 **생성·추론하지 않는다**고 규범적으로 못 박는다.

> 주문, 보유량, 비중, 현금, 노출, 손익, MDD, 유효 레버리지, **집중도**

따라서 스펙 배점표의 두 항목은 현재 정의대로는 계산할 입력이 없다.

| 항목 | 배점 | 문제 |
|---|---|---|
| 위험 한도 준수 | 20 | 온보딩 문항이 **정성 3단계**(낮음/보통/높음)라 "한도 초과분"을 계산할 수 없다 |
| 자산 집중도 | 10 | item당 자산이 하나면 **개념 자체가 성립하지 않는다** |

**어디서 정하는가** — `evaluationPlanRef`가 가리키는 **외부 승인 rubric**이 *"각 평가 항목의 공개 정보·행동·시장 checkpoint와 증거 부재 처리 규칙"*을 정의하도록 되어 있다. **이 rubric은 아직 작성되지 않았다.**

> 상세 선택지와 제안은 `03-survey/02-investor-profiling-questionnaire.md` §4 참조.
> **제안: 「위험 인식 일관성」으로 재정의** — 선언한 변동 수준과 실제 판단·근거의 정합으로 측정하고, 「자산 집중도」는 「판단의 일관성」에 흡수.

## 5. ⚠️ A3 · 문서 머지가 막혀 있다 — 프로세스 사실

`backend/README.md`와 `spec-alignment.md`에 따르면

- backend는 제품 명세를 **`docs/product-spec` Git submodule**로 버전 고정한다
- 현재 pin 대상은 **docs `main`의 커밋 `fc412a0`** → `spec/README.md`
- *"upstream 문서는 `feelgood-safe-t/docs`에서 먼저 수정·검증·commit·push한 뒤 backend gitlink를 갱신한다"*

**따라서 우리 기획·리서치·설문·UI 문서는 아직 backend의 참조 대상이 아니다.** `docs/initial-planning-docs` 브랜치에만 있고 `main`에 머지되지 않았기 때문이다.

> ✅ **필요한 조치 — PR #1 머지 요청**
> https://github.com/feelgood-safe-t/docs/pull/1
> 머지되어야 ① 백엔드가 온보딩 설문 명세와 채점 연결을 submodule로 참조할 수 있고 ② 팀 전체가 `main` 하나만 보면 된다.
